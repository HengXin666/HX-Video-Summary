三大关键设计原则
1
反馈修复 · 最小切片
用户说"节奏太快" → 不是重做整章
先定位层面：
▸ 节奏 / 视觉 / 内容 / 代码
▸ 只改最小切片
不把已做对的部分也改掉
2
多Agent · 严格隔离
每个Agent独立开发不冲突：
▸ 独立文件夹（物理隔离）
▸ 独立CSS前缀（命名隔离）
▸ 全局主题变量兜底统一
3
硬性自检 · 禁止目测
解决"自评失真"问题：
▸ 逐项核对检查清单
▸ 开独立Reviewer Agent
▸ 禁止目测一遍就放行
写代码的 Agent 自己评价 → 大概率"还不错" → 必须引入独立质检
多 Agent 协作的两种模式
Subagent
像 子进程
各自独立上下文
完成后交回结果
互不可见、不讨论

适合：并行开发多章节
优势：省 Token、易调度
结果导向型任务
VS
Agent Teams
像 项目小组
组长 + 多个组员
互相发消息
共享任务列表

适合：质检来回反馈
代价：Token 开销更高
需要来回反馈的任务
Subagent = 三人分别去三个城市办事后回来汇报 ｜ Agent Teams = 三人进同一间会议室边讨论边改

章节开发的三种模式
模式一：逐章确认
▸ 每章开发完 → 停下
▸ 人工验收 → 再继续
▸ 最稳妥，最适合初稿
最安全
模式二：顺序推进
▸ 第一章验收通过
▸ 后续章节顺序完成
▸ 基准已定，不再逐章停
效率平衡
模式三：并行开发
▸ 第一章验收通过
▸ 后续多Agent并行写
▸ 最多同时3个Agent
最高效率
经验：最多同时并行 3 个 Agent 比较合适
必须选能力较强的模型，否则多Agent调度容易出错
第一章定调：字体、间距、动效节奏全在第一章确定
后续章节继承第一章的视觉基调和代码规范
