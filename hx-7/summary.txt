PRCP社区2025年终技术分享大会 — 内容总结

【视频标题】[cpp] 某会议 回放 2025-12-20 女生自用99新

【核心概述】

这是PRCP（Pure/Rich C++ Protocol）社区在2025年底举办的技术分享会议回放，共包含三个主题演讲：社区年度总结与未来规划、DWARF调试信息深度剖析、以及基于std::execution的现代化Actor框架ES Actor。

================================================================================

一、PRCP社区2025年度总结与2026年规划（社区负责人）

【2024年计划清单回顾】
社区负责人在2024年底制定了2025年的计划清单，回顾后发现完成三项核心任务：
1. 基于反射库的重构已完成
2. RestRPC从C++11升级到C++20（回调函数全面替换为协程）
3. 雅兰叮库的RDMA功能已实现（2025年最重要的特性之一）

【RestRPC现代化升级亮点】
- 服务注册和客户端调用全部基于协程（C++20 coroutines）
- 内置订阅/发布（Pub/Sub）功能：服务端publish，客户端subscribe，框架自动序列化/反序列化
- 默认使用StructPack序列化协议，支持替换为自定义协议

【2026年规划清单】
1. 反射库重构：利用C++26反射特性替换现有的非标准hack手段，同时在C++26之前做好预编译兼容处理
2. PRCP社区网站大改版：自2015年创办以来首次重大改版，包含四大新模块：
   - 问答版块：邀请社区专家解答C++初学者的疑问（目标3天内回复）
   - 统一聊天室：类似Slack模式，为每个开源项目建立独立频道，逐步替代分散的QQ群/微信群/钉钉群
   - Code Review：专注C++代码评审和重构建议
   - 社区服务：招聘/求职/开源项目协作信息发布
3. ORM库升级：协程化/异步化改造，支持类似C# LINQ的链式流式API调用

二、DWARF调试信息格式深度剖析（袁志浩·赛姆匹克工程师）

【DWARF基础概念】
- DWARF是Linux下最常用的调试信息格式（gcc -g 选项产生）
- 与Windows PDB不同：DWARF是一种数据格式而非文件格式，依附于ELF/Mach-O/PE等容器格式存在
- DWARF以Section组织数据，常见Section包括.debug_info、debug_line等

【DIE树结构（Debugging Information Entry）】
- DIE是一棵巨大的树，用于收集程序中的元素（函数、类、命名空间等）
- 每个Compilation Unit对应一棵以DW_TAG_compile_unit为顶层的DIE树
- DIE类别与编程语言无关（C++类和Fortran类用同一种DIE表示）

【Line Program机制】
- 将指令地址映射到源代码行/列的巨型矩阵
- 二进制存储形式是一个状态机（需要"解释执行"）
- 调试器的行断点依赖此机制；未记录的行无法设置断点

【函数的三种表示】
1. 声明（Declaration）：有名字，无地址范围
2. 定义（Definition）：有地址范围，通过DW_AT_specification指向声明
3. 外联实例（Out-of-line Instance）：用于内联函数的具体实现

【Lambda与内联处理】
- GCC通过DW_AT_artificial属性标记Lambda的operator()，可直接识别Lambda表达式
- 内联展开使用DW_TAG_inlined_subroutine DIE，通过DW_AT_ranges支持多个内联代码段

【工具化DWARF的实践问题】
- 性能瓶颈：构建parent指针回溯完整限定名（qualified name），但可预处理好所需DIE
- 并行化：不同ELF文件间天然支持多进程并行
- 名字还原：demangling需要完整AST解释，推荐LLVM的itanium-demangle
- 编译器怪癖：Clang tail-merge/vtable-hoist优化可能导致控制流与源码不对应
- 推荐工具：pyelftools（Python库）、llvm-dwarfdump（LLVM版本，不推荐GNU binutils版本）

三、ES Actor框架：基于std::execution的现代C++ Actor框架（魏李欣·强向投资）

【Actor模型概述】
- 1973年提出的并发编程范式，核心是"消息传递"而非"共享内存"
- 每个Actor有独立的Mailbox（先入先出队列），消息串行处理
- 三大优势：
  1. 无需关心线程安全（单Actor内单线程执行）
  2. 全局纯异步无阻塞
  3. 无缝跨网络（本地内存传递 vs 远程自动序列化/网络通信）

【C++ Actor框架现状与痛点】
- 现有方案要么一个Actor开一个线程（资源浪费），要么API晦涩侵入性强（如CAF、SObjectizer）
- CAF全称"C++ Actor Framework"，名字直接占满了Google搜索结果

【ES Actor的设计理念】
- 基于std::execution（C++26标准），未来所有C++异步库的统一底座
- API设计追求极简："写一个类就能定义出一个Actor"
- 调度器可插拔（Pluggable Scheduler）：兼容任何符合std::execution规范的调度器
- 开箱即用四种调度策略：
  1. Work-Sharing：无锁队列线程池（默认，适合通用场景）
  2. 优先级队列线程池：支持Actor优先级调度（适合高吞吐场景）
  3. 绑核（Core-Affinity）调度器：Actor固定运行在指定CPU核心（适合低延迟场景）
  4. Work-Stealing线程池：绑核基础上允许线程间"偷任务"（延迟与负载均衡的折中）

【生产实践：特征计算框架】
- 在线模式（低延迟）：每个算子一个Actor + 默认无锁队列调度器
  - 性能数据：32核机器上13ms跑完6万个Operator Actor，调度开销占比极小
- 离线模式（高吞吐）：每个算子多个Actor（数据分片）+ 优先级队列调度器
  - 优先级调度使下游Actor先算完，降低内存压力，提升整体吞吐

【技术特点】
- 底层通信基于ZeroMQ
- Mailbox采用MPSC队列（mutex + std::deque），线性化保证
- 正在开发Mailbox分裂优化（用户显式指定partition ID，进一步降低延迟）
- 分布式支持：跨节点创建Actor，无需额外服务发现机制

================================================================================

【总结与启示】

1. C++生态正在迎来协程化和标准化的浪潮：从RestRPC全面采用C++20协程，到ES Actor基于C++26 std::execution，都体现了社区向现代C++快速演进
2. 底层基础设施（如DWARF）蕴含着深厚的工程知识，对工具开发者而言理解其内部机制至关重要
3. Actor模型在C++生态中仍有巨大潜力：结合C++26统一异步标准，有望催生繁荣的异步库生态
4. PRCP社区持续推动中文C++技术圈的发展，从开源项目到知识分享，十年耕耘成果斐然
